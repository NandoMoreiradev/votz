# Mensagens privadas cifradas — implementação e validação

Data: 18/11/2026. Complementa o [plano de comunicação e Pulso](../negocio/comunicacao-e-pulso.md).

## Escopo desta entrega

Texto em conversas individuais aceitas, com verificação manual de identidade, histórico cifrado, fila local durável, repetição idempotente e recibos de entrega/leitura. Web e mobile compartilham a máquina de transporte em `packages/chat-core`; cada plataforma usa um adaptador para o motor criptográfico Rust do Matrix.

Grupos continuam com a gestão de convites, participantes e funções já implementada. Esta etapa não habilita texto em grupos, anexos, chamadas ou Pulso. Esses recursos têm etapas próprias, especialmente rotação de chaves ao remover participantes e proteção dos anexos.

## Arquitetura

- Synapse 1.165.0, sem modificações, opera como transporte privado, sem federação nem registro público. No ambiente local, a porta 8008 só aceita conexões em loopback; a base PostgreSQL e a identidade de serviço são separadas.
- O aplicativo acessa exclusivamente a API autenticada do Votz. O gateway valida identidade pessoal, e-mail confirmado, dispositivo, aceite da conversa, participação e bloqueios. Não há proxy aberto para rotas arbitrárias do Matrix.
- O usuário Matrix deriva do UUID Votz. Tokens de acesso ao transporte ficam cifrados na base do servidor, com chave dedicada; não são entregues ao cliente. Esses tokens não são chaves de decifração das mensagens.
- O servidor aceita apenas envelopes cifrados Megolm nas mensagens. Eventos entre dispositivos são restritos a envelopes Olm e à negociação pública de verificação SAS. Campos inesperados são recusados.
- A sala é privada. Usuários comuns não podem alterar seu estado, convidar pessoas ou enviar eventos de texto em claro. A participação Votz continua sendo a autorização principal.
- Bloqueios e envios compartilham o bloqueio transacional da conversa. Um bloqueio concluído impede novos envios. O histórico anterior permanece disponível aos participantes.
- A identidade do remetente é conferida contra o dispositivo verificado e suas chaves públicas antes de exibir texto. Decifrar um evento não significa confiar automaticamente no remetente.

## Dispositivos e armazenamento

O piloto permite **um dispositivo cifrado por conta**. Uma tentativa de ativar outro dispositivo é recusada; não substitui chaves silenciosamente. Para testar Android contra web, use duas contas distintas.

No navegador, o SDK oficial `@matrix-org/matrix-sdk-crypto-wasm` 19.0.1 mantém seu armazenamento IndexedDB cifrado com uma senha de pelo menos 12 caracteres escolhida pelo usuário. A senha não é persistida nem enviada à API. Web Locks impedem duas abas de escrever simultaneamente no mesmo armazenamento. O módulo WASM é carregado sob demanda ao desbloquear as conversas; não integra o caminho inicial do feed.

No mobile, `react-native-matrix-crypto` 0.8.0 usa o motor nativo Rust. A senha aleatória do armazenamento fica no SecureStore, restrita ao aparelho. O estado de transporte usa dois arquivos alternados para conservar o último registro completo se o processo for interrompido. A ponte declara peer dependency RN 0.87; o projeto usa RN 0.88.1 e um override específico. A compatibilidade só será considerada comprovada depois da build e dos testes nativos Android e iOS.

O texto decifrado e o rascunho ficam na memória. A fila persistida contém envelopes cifrados, identificadores e recibos; não contém o corpo em claro. O envio só é agendado depois de gravar a fila. Repetições usam o mesmo identificador de transação. A fila de mensagens limita-se a 100 itens; falhas permanentes permanecem disponíveis para tentativa explícita.

A memória é limpa ao fechar o cliente. O mobile também encerra a sessão de chat ao sair da tela ou colocar o aplicativo em segundo plano.

## Significado dos estados

| Estado | Critério |
| --- | --- |
| Aguardando envio | Envelope gravado localmente; o servidor ainda não confirmou. |
| Enviada | Transporte aceitou o envelope e retornou seu identificador. |
| Entregue | O outro cliente autenticou e decifrou a mensagem e confirmou à API. |
| Lida | O destinatário ativou o compartilhamento de leitura e a mensagem ficou visível por pelo menos 500 ms. |
| Não enviada | Erro definitivo preservado na fila cifrada; permite tentativa explícita. |

A leitura vem desativada por padrão. Desativá-la não apaga recibos já compartilhados. O servidor verifica que cada recibo se refere a uma mensagem recebida naquela conversa; não aceita confirmar a própria mensagem ou eventos de terceiros. Uma confirmação tardia de entrega não regride um recibo de leitura.

Esses recibos são declarações do cliente destinatário. O servidor não consegue provar que uma pessoa efetivamente leu o texto.

## Preparar o ambiente local

Com PostgreSQL e Redis locais em execução:

```powershell
node packages/chat-crypto-lab/setup-local-server.cjs
docker compose -f docker-compose.chat.yml up -d
npx.cmd dotenv -e .env -- npm.cmd exec --workspace=packages/database -- prisma migrate deploy
npm.cmd run build --workspace=packages/chat-core
npm.cmd run build --workspace=apps/api
```

O script conserva segredos existentes e cria arquivos ignorados em `.local/chat` e `apps/api/.env.local`. Não execute contra uma base remota. A configuração inicial mantém `CHAT_TEXT_ENABLED=false`; habilitar o piloto local exige também `CONVERSATIONS_ENABLED=true`. O `.env.example` mantém ambos desativados.

Novas dependências nativas exigem uma development build pelo EAS. O APK antigo não consegue abrir o motor cifrado e deve apresentar uma instrução de atualização. Android Studio não é necessário.

## Verificação reproduzível

```powershell
npm.cmd test --workspace=packages/chat-core
npm.cmd test --workspace=packages/chat-crypto-lab
npm.cmd test --workspace=apps/api -- --runInBand conversations.spec notifications.gateway.spec route-auth
# API de teste em localhost:3001, com CHAT_TEXT_ENABLED=true:
npx.cmd dotenv -e .env -- node apps/api/test/chat-text.integration.cjs
# Requer Playwright/Chromium; VOTZ_PLAYWRIGHT_MODULE pode indicar instalação isolada:
npx.cmd dotenv -e .env -- node apps/web/test/chat-text.browser.cjs
```

Os testes de integração criam e removem suas próprias contas Votz locais. O transporte privado pode conservar salas cifradas desses testes, sem vínculos com contas Votz existentes.

O teste real usa o mesmo adaptador WASM do navegador e o Synapse local, com SAS comparado explicitamente. Exercita troca nos dois sentidos, Unicode, histórico cifrado, rejeição de texto em claro, acesso de terceiros, não substituição de dispositivo, repetição sem duplicação, bloqueios e privacidade dos recibos.

O teste de navegador cobre ativação, persistência IndexedDB, comparação SAS, duas contas, larguras de 1440/390/320, exclusividade de aba, falha de rede, reinício, senha incorreta e retomada da fila.

### Resultados desta rodada

- Núcleo de transporte: **8 testes aprovados**, incluindo falha de gravação antes do envio, repetição idempotente, limite da fila, limpeza de memória, remetente não verificado e recibos condicionados a consentimento e visibilidade.
- Regressões da API: **18 testes aprovados**, incluindo autorização de rotas, gateway e gestão de conversas.
- Laboratório do SDK: **2 provas aprovadas**, incluindo adulteração, terceiros e rotação após remoção.
- Integração com SDK WASM, API, PostgreSQL e Synapse reais: aprovada, com **93 operações HTTP** na última execução. A contagem varia com a sincronização. Também consulta diretamente o PostgreSQL do Synapse e confirma eventos cifrados sem o texto dos testes.
- Navegador em desenvolvimento: aprovado nos dois sentidos, incluindo leitura opcional pela interface, persistência após reinício, senha incorreta e retomada sem duplicação. A restauração de pendências usa um identificador Matrix válido ao apresentar o envelope local ao SDK; o identificador da fila permanece separado.
- Web: **build de produção e teste completo em preview aprovados**, com CSP ativa, WASM, leitura opcional, reinício e retomada sem duplicação. Para repetir, configure `FRONTEND_URL` para a origem de preview e use Redis de testes isolado; não se desativa o CSRF nem os limites de autenticação. Evidências: [desktop](evidence/chat-text-2026-11-18/web-desktop.png), [390 px](evidence/chat-text-2026-11-18/web-390.png), [320 px](evidence/chat-text-2026-11-18/web-320.png).
- Mobile: tipos e lint aprovados; JavaScript Android e iOS exportado. **Builds nativas Android e iOS de simulador concluídas com sucesso pelo EAS.** Execução e interoperabilidade em aparelhos continuam pendentes.

Build Android concluída: `b4e799f3-c92d-4243-8103-b49a5120a43a`, perfil development. Build iOS de simulador concluída: `cb55bbb9-0f57-436d-80ef-0d82664bdbb5`, perfil development-simulator. Esse perfil segue a [configuração oficial de simuladores do Expo](https://docs.expo.dev/build-reference/simulators/). Não equivale a uma distribuição iOS assinada para aparelhos nem a uma validação de interface em iPhone.

O ensaio no aparelho depende de o Android voltar a aparecer no ADB. Nenhum teste WASM, exportação de JavaScript ou resultado de compilação substitui essa verificação.

O APK foi baixado integralmente para o arquivo ignorado `apps/mobile/.expo/chat-development.apk`. A estrutura ZIP contém o manifesto e as bibliotecas Matrix para as quatro ABIs Android. O [registro da build](evidence/chat-text-2026-11-18/android-build.json) conserva tamanho e SHA-256, sem incluir o binário no repositório. É uma build de desenvolvimento com múltiplas ABIs e símbolos; seu tamanho não representa o download de uma distribuição otimizada por aparelho.

A ponte nativa exige a sequência `shareScopeKey → claim/pump → shareScopeKey → pump` antes de cifrar para um dispositivo novo. O adaptador preserva essa ordem e entrega os avisos públicos `m.room_key.withheld` pelo gateway, com campos restritos. A negociação SAS recebida é aceita pelo SDK; a confiança continua exigindo comparação e confirmação explícitas pela pessoa.

## Requisitos antes da liberação pública

1. Concluir execução e interoperabilidade Android/web e validação nativa em iOS. A compilação nativa passou nos dois sistemas; isso ainda não comprova comportamento no dispositivo ou simulador.
2. Implementar troca, revogação e recuperação de dispositivo, proteção reforçada da ativação e backup cifrado das chaves. Hoje perder o dispositivo ou a senha pode tornar o histórico inacessível; não há recuperação silenciosa.
3. Revisar o modelo de ameaças, operação de chaves administrativas, auditoria das dependências e avaliação externa de segurança. O uso de um SDK reconhecido não substitui essa revisão.
4. Provisionar ambiente de homologação com TLS, gestão de segredos, backups testados, atualização do Synapse, observabilidade sem conteúdo privado, retenção e resposta a incidentes. O compose local não é uma implantação de produção.
5. Executar testes de carga, quedas, sessões expiradas, múltiplas instâncias e limites operacionais. O piloto usa sincronização longa do transporte; push para aplicativo fechado é outra etapa.
6. Revisar avisos/licenças: SDK WASM e ponte nativa Apache-2.0; Synapse AGPL-3.0. Preservar avisos e cumprir as obrigações da distribuição/operação escolhida.
